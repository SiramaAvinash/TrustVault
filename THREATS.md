# TrustVault Threat Model

## Assets
- Confidential document bytes and metadata
- User credentials and bearer tokens
- Document grants and ownership
- Audit events and integrity chain
- Application secrets and database

## Trust boundaries
- Browser to API
- Authenticated user to document-specific authorization
- API process to private file storage
- API process to database
- Administrator to ordinary user
- Local deployment to production deployment

## Threats and controls
| Threat | Control in this starter | Remaining concern |
|---|---|---|
| IDOR/BOLA document ID guessing | Every document operation resolves the document and checks current access on the server | Must test every future endpoint |
| Cross-user leakage | List/search filters to owned or granted documents; file bytes never public | Metadata fields added later need same checks |
| Stale access after revocation | Grants are checked from DB for every request; no public or long-lived file URLs | A file already downloaded cannot be recalled |
| Privilege escalation | Role is read from DB; grant/edit/delete operations require owner or admin rules | Production should include account lifecycle and MFA |
| Unauthorized download | Download endpoint checks current access before reading private storage | Browser/client caching must be considered |
| Malicious/oversized upload | Size limit, extension allowlist, generated name, basic signature checks | Add antivirus/CDR and deeper format parsing |
| Path traversal | Storage filename generated by server, not user filename | Keep storage directory inaccessible from web server |
| Audit alteration | SHA-256 hash chain and verification endpoint | Full DB/server administrator can rewrite all records and chain |
| Audit omission | Successful and denied access attempts are recorded in application code | Database compromise can remove events |
| Password theft | Argon2 password hashing; optional email OTP | Add robust lockout, rate limiting, breach monitoring |
| Forged Google identity token | Google ID token signature, issuer, expiry, and audience verified server-side; email must be verified | Live provider verification requires configured Google Client ID and network access; run a production smoke test |
| Token theft | Short-lived JWT bearer tokens | Add refresh/logout strategy, secure transport, token revocation |
| SQL injection | SQLAlchemy parameterized queries | Review raw SQL if introduced |
| XSS | React escapes ordinary text by default | Avoid dangerouslySetInnerHTML; sanitize rich text |
| CSRF | Bearer token sent in Authorization header, not cookie | Reassess if switching to cookies |
| CORS abuse | Explicit local frontend origin | Configure exact production origin |
| Secrets committed | `.env` ignored; examples use placeholders | Rotate any secret accidentally committed |
| Storage exposure | Private backend storage folder | Deployment must not mount it as public static content |
| Account deactivation | Each request checks active user in database | Add admin account disable controls before production |
| Brute force/DoS | Not implemented in starter | Add rate limiting, request quotas, reverse proxy limits |
| Concurrent audit writes | DB transaction protects each event creation | Production should use robust DB isolation and external checkpoints |
| Backup exposure | Not implemented | Encrypt backups and restrict restore access |

## Security assumptions
- The API host and its operating system are trusted.
- A user cannot access backend storage or the SQLite file directly.
- HTTPS is used in production.
- File sharing is not a substitute for secure endpoint authorization.
- Audit hash chaining is tamper-evident, not truly immutable without independent checkpoints.

## Google sign-in notes
- The browser submits Google's ID token credential; it does not submit trusted user identity fields.
- The backend validates the token against the configured Google Web client ID.
- New Google identities receive the least-privilege Viewer role. Role promotion remains administrator-only.
- Automated tests use mocked verified claims for account-flow behavior; they do not prove Google's live signature service is reachable or that the OAuth consent screen is configured correctly.

## Before production
1. Use PostgreSQL and managed secrets.
2. Serve only over HTTPS and configure strict CORS.
3. Add rate limiting, MFA, account disablement, and session/token revocation.
4. Add antivirus scanning and content disarm/reconstruction for office/PDF files.
5. Put audit checkpoints in an independently controlled append-only system.
6. Add encrypted backups and a tested restore process.
7. Conduct a professional security review and penetration test.

## Additional threats introduced by enhanced features

- **Registration and privilege escalation:** public registration always creates a Viewer. Role changes require an administrator API request. Never accept `role` from registration payloads.
- **Account deactivation:** disabling an account must prevent token use and revoke active grants so reactivation does not silently restore old access.
- **Grant expiry:** expiry is checked server-side on every request; frontend timers are not an authorization control. Store timestamps consistently in UTC.
- **Email delivery and 2FA:** Resend API credentials belong in environment secrets. OTP values are short-lived, hashed in storage, one-use, and attempt-limited. Add rate limiting, verified email ownership, recovery procedures, and delivery monitoring before production.
- **Watermark limitations:** a watermark deters casual redistribution but cannot prevent screenshots, OCR, or alteration. Do not claim it is DRM.
- **Version history:** version files are private and use the same authorization policy as the parent document. Restoration must snapshot the current file first and recompute SHA-256.
- **Approval workflow:** a pending/rejected approval must block new grants at the API layer. UI status alone is insufficient.
- **Notification metadata:** avoid including document contents or secrets in email. Audit recipient and send outcome without storing passwords or OTPs.
- **Integrity checks:** compare the actual file digest to the stored digest before download. A database attacker able to rewrite both file and digest may defeat this check; use independently protected manifests/checkpoints for stronger guarantees.
- **Analytics leakage:** restrict event and document counts to the caller's authorized scope; do not expose global totals to ordinary users.


## Added access-request and session threats

| Threat | Mitigation in this build | Residual limitation |
|---|---|---|
| Viewer downloads a read-only document | Download endpoint checks explicit download/edit permission; read permission only supports metadata/inline preview | A preview can still be captured or saved by the browser |
| User requests a stronger permission | Owner receives an access request; approval requires OTP to owner's configured email; grant expires after one hour | Email-provider/mailbox compromise can undermine OTP; use stronger phishing-resistant authentication in production |
| Attacker knows password and signs in from a new browser/IP | Email OTP challenge when Resend is configured; account 2FA challenges every sign-in when enabled | IP/user-agent recognition is heuristic, not device identity |
| Same account has simultaneous sessions | Session records, concurrent-session audit event, optional email to active administrators | Multiple sessions may be legitimate; alerts require investigation |
| User's session token is revoked | Session ID is embedded in the JWT and checked against the session table on each authenticated request | A fully compromised server/database can alter session state |
| User tries an unauthorized document operation | API checks permission and records denied event; owner notification is sent when Resend is configured, grouped for 10 minutes per actor/action/document | If Resend is unavailable, audit works but email alert delivery does not |
| Administrator attempts to read another user's private document | Admin user-management privileges do not automatically bypass document authorization | Production deployments should also segregate operational roles and protect database/storage access |

Do not claim this starter is production-certified. Before real confidential use, add independent email verification, passkeys/WebAuthn, robust rate limiting, CSRF protections for cookie-based auth, malware scanning, encryption/key management, off-host immutable audit checkpoints, backups, monitoring, and a professional security review.
